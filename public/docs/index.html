4. Going-live checklist

The app currently runs against the dev Sharetribe environment. To launch:

  1. In Sharetribe Console, complete the Go live flow (paid Sharetribe plan) to get a Live environment.
  2. Create a new application under the Live environment (Console → Build → Advanced → Applications) and put its client ID/secret into Heroku config vars (REACT_APP_SHARETRIBE_SDK_CLIENT_ID, SHARETRIBE_SDK_CLIENT_SECRET).
  3. Push the transaction process to the Live environment and recreate the alias: 
    flex-cli login
flex-cli process create --path ext/transaction-processes/fashion-rental --process fashion-rental -m <live-marketplace-id>
flex-cli process create-alias --process fashion-rental --version 1 --alias release-1 -m <live-marketplace-id>
  4. Recreate Console configuration in Live (listing fields size, occasion, condition, categories, branding) — Console content does not copy automatically from dev to live.
  5. Connect Stripe in live mode: live secret key into Console → Payments, live publishable key into Heroku (REACT_APP_STRIPE_PUBLISHABLE_KEY).
  6. Create a Live Integration API application and update the two SHARETRIBE_INTEGRATION_SDK_* vars.
  7. Sign up for Mapbox (free) and set REACT_APP_MAPBOX_ACCESS_TOKEN.
  8. Optionally add a custom domain in Heroku (Heroku custom domains) and update REACT_APP_MARKETPLACE_ROOT_URL.
  9. Run the testing checklist end to end with a real card in test mode first.

5. Transaction process (fashion-rental)

Custom manual-capture purchase process. Definition: ext/transaction-processes/fashion-rental/process.edn; client mirror: src/transactions/transactionProcessFashionRental.js. Pushed to the marketplace as fashion-rental, alias release-1.

  1. Order placed — customer pays; the card is authorized only (funds held, not captured). State: preauthorized.
  2. Lender accepts — payment captured. Auto-captures after 7 days if the lender doesn't respond; auto-declines (full release of the hold) after 14 days.
  3. Shipping — lender marks shipped; customer marks received (auto after 14 days). Payout to the lender is created when the order is received.
  4. Disputes — customer can dispute after delivery; operator resolves (received or canceled with refund).
  5. Reviews — both parties review after completion; double-blind publishing.

All 30 notification email templates live in ext/transaction-processes/fashion-rental/templates/ and are pushed together with the process.

6. Sharetribe Console configuration

Important: the Console "Listing types" screen only offers Sharetribe's built-in processes. The custom fashion-rental process is bound in code: src/config/configListing.js defines the listing type, and src/util/configHelpers.js is modified to merge code-level listing config over the hosted config. Do not switch the Console listing type — leave it as is.
  • Listing fields (Console → Listings → Listing fields): size (text), occasion (multi-enum, searchable — powers the home-page occasion links and search filtering), condition (enum). Occasion option IDs must match the ones used by the home page section (wedding, date-night, party, …).
  • Listing categories: managed in Console → Listings → Listing categories.
  • Existing listings caveat: listings created before the process switch carry their old process alias. Re-save each one through the edit wizard (or recreate) so it picks up fashion-rental/release-1. New listings are correct automatically.

7. Cart & multi-lender checkout

  • Add to cart: button on every purchasable listing page. Cart persists in the browser (localStorage) and groups items by lender. Cart icon + drawer in the top bar.
  • Checkout (/cart/checkout): because Sharetribe transactions are one-listing-per-transaction, the checkout places one order per cart item, sequentially, showing per-item progress. A single shipping address is collected and attached to every order.
  • Payment: requires a saved default card (Account settings → Payment methods). The saved card is attached to the customer's Stripe customer, which is what allows it to be charged across multiple payment intents in one run. Users without a saved card are prompted to add one first.
  • Failure behavior: items ordered successfully leave the cart immediately; on a failure (e.g. card declined) the sequence stops and the remaining items stay in the cart for retry. Unaccepted authorizations are released automatically by the process.

Key files: src/ducks/cart.duck.js, src/containers/CartCheckoutPage/CartCheckoutPage.js + .duck.js.

8. Card holds

  • Lenders set an optional hold amount when pricing a listing (stored as publicData.holdAmountCents).
  • At checkout the hold is added to the customer's total as a Card hold line item (customer-side only — it is not part of the lender payout, so the marketplace operator can refund it after the item comes back in good condition).
  • The entire amount (rental + shipping + hold) is preauthorized at checkout and captured when the lender accepts. If the lender declines or lets the order expire, the full authorization is released — the customer is never charged.
  • Feature toggle: enableCardHolds in src/config/configFeatureFlags.js. Server logic: server/api-util/lineItems.js.

9. Listing collaborators (multi-user product management)

  • Owners add collaborators by email from the "Collaborators" tab in the listing edit wizard. The email must belong to an existing marketplace user.
  • Collaborators see shared listings under Manage listings → Shared with me and can edit details, pricing, stock, delivery and location. Photos, availability, publishing and the collaborator list itself remain owner-only.
  • All permission checks happen server-side: the caller's identity comes from their login session, and membership is verified against the listing before any change. Collaborators cannot modify the collaborator list or private data.
  • Requires the two SHARETRIBE_INTEGRATION_SDK_* environment variables. Without them, adding collaborators still works but grants no access yet.

Key files: server/api/listing-collaborators.js, server/api-util/integrationSdk.js, src/util/collaborators.js.

10. Favorites, occasions, AI assist

Closet-style favoriting

Heart button on listing cards and listing pages; favorites saved to the user's profile and shown on /favorites (linked from the top bar when logged in). Toggle: enableFavoriting.

Shop by occasion

The home page shows a "Shop by occasion" pill row (wedding, date night, party, …). Each pill links to search filtered by the occasion field. Options are read live from the Console listing-field config, so renaming options in Console updates the section automatically. Component: src/containers/LandingPage/SectionOccasions.js.

AI listing assist

When creating a listing, the lender can generate a suggested description, size and occasion tags from the listing title/photos context. "Apply" fills any fields the lender hasn't already filled — it never overwrites manual input. Requires ANTHROPIC_API_KEY. Server: server/api/ai-listing-assist.js.

11. Testing checklist

  1. Create two lender accounts, complete Stripe onboarding for each (test mode: use Stripe's test data), and publish one listing each with a price, shipping fee and a card hold amount.
  2. As a customer: save a card under Account settings → Payment methods (Stripe test card 4242 4242 4242 4242).
  3. Add both listings to the cart, open the cart, proceed to checkout — verify the order is split per lender and both orders complete, and that each order breakdown shows the item, shipping and Card hold lines.
  4. As each lender: accept one order, decline the other. Verify capture on accept and full release on decline (Stripe dashboard → Payments).
  5. Mark the accepted order shipped (lender) then received (customer); verify the lender payout is created and both parties can leave reviews.
  6. Add a collaborator by email to a listing; log in as the collaborator, edit the price from "Shared with me", and verify the change saved.
  7. Favorite a listing, check /favorites; click a home-page occasion pill and verify search filters.
  8. Create a listing with AI assist and apply the suggestions.
